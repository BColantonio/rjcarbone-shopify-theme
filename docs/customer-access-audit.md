# Customer access audit

## Scope and conclusion

This is a source inspection of the theme and existing requirements, not a live-store, checkout, API, or Shopify-admin configuration test. The theme generally shows prices and purchase controls without checking whether a customer is signed in or approved. Availability and theme settings control some UI, but neither establishes wholesale eligibility. No explicit wholesale-approval check or server-side ordering enforcement was identified in the inspected repository; this does not prove what an independently configured Shopify store or external service enforces.

The user reports **Basic** as the current development plan; the launch plan will be reevaluated before launch. This is not an independent Admin verification, and the customer-account configuration remains unverified.

The [confirmed wholesale requirements](./wholesale-registration-requirements.md#confirmed-requirements) allow visitors and unapproved accounts to browse but prohibit seeing any prices or placing orders. Price confidentiality includes HTML, structured data, JavaScript payloads, and public APIs. **Signing in is not approval.** Applications are to be reviewed by Brian or his supervisor; approval and revocation are manual, case-by-case decisions. Existing customers automatically qualify after secure identity matching. The [launch checklist](./launch-readiness-checklist.md#shopify-10-launch-readiness-checklist) distinguishes source and preview evidence from production proof.

## Missing visitor and pending-approval experiences

- **Visitor:** The theme does not provide the required browse-without-prices or no-order experience: the identified price, Add, cart, and checkout paths do not distinguish an unapproved visitor. The login and preview links are present, but the preview is not a real application submission. A login prompt is not a substitute for an approval explanation.
- **Signed-in, pending, or declined applicant:** The theme has no verified approval/pending signal to distinguish these states from an approved customer. There is no reliable pending-status message, no real submission or Brian/supervisor-review workflow, and no approval-dependent presentation or ordering block in the inspected paths. Do not infer pending or approved from `customer` being present.
- **Existing, approved, or revoked customer:** Existing customers qualify after secure identity matching, but the inspected theme has no verified matching, approval contract, or revocation handling. The matching mechanism, authoritative record, and propagation are still to be designed ([requirements, migration](./wholesale-registration-requirements.md#existing-customer-migration)).

The application stays **preview-only**: [`sections/wholesale-application-preview.liquid:1-30`](../sections/wholesale-application-preview.liquid) displays the prototype notice, and the [requirements](./wholesale-registration-requirements.md#confirmed-requirements) and [launch checklist](./launch-readiness-checklist.md#completed-and-verified) state that it does not submit applications, create accounts, upload documents, or grant access. No pending state can be inferred from using it.

## Smallest next implementation and decisions

**Can be built now, independently of an approval contract:** Add or refine neutral, clearly preview-labeled account-access guidance that explains that sign-in does not grant wholesale approval and that the application is not submitted. Keep it independent of customer identity or inferred application status, preserve browsing and existing cart behavior, and test the rendered copy and links. This is informational only: it neither implements the required visitor/pending restrictions nor makes the store launch-ready. The prototype must remain preview-only.

**Requires team and backend/store decisions before implementing gating:**

1. Confirm the store's actual plan, account mode, publication channels, Markets and catalog capabilities in Admin; none is established by theme settings. Select and prove an architecture against the already-confirmed strict rule ([requirements, plan evidence and comparison](./wholesale-registration-requirements.md#plan-and-account-dependencies)).
2. Prototype a separate price-free public catalog with isolated authenticated commerce. This is a candidate, not a verified Shopify configuration: prove that all Shopify product, search, cart and checkout surfaces are inaccessible to unapproved users without breaking approved ordering. If isolation is not possible, select a different backend/commerce architecture.
3. Define secure existing-customer matching, manual decisions, authoritative approval state, operator permissions, and revocation propagation. Company/location assignment is only a possible access input, not a configured or confirmed approval signal. Do not invent a tag, metafield, or Shopify setting.
4. Build presentation only after the contract exists, and independently implement server-side price and order enforcement. Shopify Cart and Checkout Validation is a candidate for supported checkout paths, not a price-confidentiality mechanism; verify Function plan availability, trusted inputs, fail-closed behavior, revocation and every enabled channel. Keep the application preview-only.
5. On an authorized configured environment, record negative and positive tests for anonymous, signed-in unapproved/pending, securely matched existing, approved, declined, and revoked customers. Check HTML, JavaScript, structured data, product `.js`, predictive-search JSON, tokenless Storefront API, direct cart/checkout, previously issued links, and enabled accelerated paths. Do not place live orders without authorization.

Theme visibility changes, disabled buttons, and client-side checks cannot prove either price confidentiality or server-side order enforcement. A separate public catalog alone is also insufficient if Shopify's product, cart, or checkout responses expose prices ([requirements, architecture assessment](./wholesale-registration-requirements.md#architecture-assessment)).
